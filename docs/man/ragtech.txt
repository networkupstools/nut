RAGTECH(8)
==========

NAME
----

ragtech - Driver for Ragtech UPS units (USB CDC-ACM)

SYNOPSIS
--------

*ragtech* -h

*ragtech* -a 'UPS_NAME' ['OPTIONS']

NOTE: This man page only documents the hardware-specific features of
the ragtech driver. For information about the core driver, see
linkman:nutupsdrv[8].


SUPPORTED HARDWARE
------------------

Targets Ragtech UPSes that expose a USB CDC-ACM serial interface
(USB VID 0x04D8, PID 0x000A -- Microchip PIC with CDC firmware).
The device shows up under Linux as `/dev/ttyACM*`.

Validated end-to-end against the Ragtech Easy 2000 TI (model id 16 in
the family-10 device table). The other 19 models in the same table --
Easy 600/700/900/1200/1300/1400/1600/1800/2000/2200 in both TI (115 V)
and M2 (220 V) variants, also sold under the NEP, TORO, INNERGIE and
OneUP brands in Brazil -- share the same wire protocol and register
layout and are expected to work; please report results.

Units from other Ragtech lines that share the same USB id (for example
the Easy Pro "GT" series) speak the same protocol but may report a model
id that collides with a table entry, so the driver can pick the wrong VA
rating. Use the *va* option below to set the correct rating in that case.

A second protocol, "family 14", covers the Ragtech Easy Way units (21
models, Easy Way 500/600/700/1200/1300/1400/1600 in TI, M1 and M2
variants). They use the same USB ids but a different, push-only
protocol; see the *FAMILY 14 (EASY WAY)* section below. Support for
family 14 is *read-only* and was developed from captures of the OEM
software on one unit (an Easy Way TI 1400, sold as "Easy Way 1500 VA
GT"); the other 20 models come from the OEM device table only.

This driver is *experimental*. Polling, status decoding and the
`shutdown.stayoff` / `shutdown.stop` instant commands have been
verified on hardware; `shutdown.return` and `test.battery.start.deep`
are implemented but not yet verified end-to-end (see the
*allow_shutdown* note below). The beeper-control wire encoding has
not been reverse-engineered yet.


EXTRA ARGUMENTS
---------------

This driver supports the following options in the *ups.conf*:

*family*='auto|10|14';;
Select the protocol family. The default, *auto*, first listens for a
few seconds without writing anything to the UPS: if it receives a
checksum-valid family 14 frame at 2560 baud, the unit is treated as
family 14;
otherwise the driver continues with the family 10 protocol, with the
serial settings it had before the listen. Set *family=10* on an Easy Pro
unit to skip the listen (and its start-up delay of about three seconds,
which also applies to `-k`) and to leave the port settings exactly as
earlier versions did. Set *family=14* to require the Easy Way protocol;
owners of an Easy Way unit are advised to do so, because if the automatic
listen ever misses the stream, the driver falls back to polling it with
family 10 commands, which that protocol does not use.

*iout_calib*='number';;
Per-unit output current calibration constant. If omitted (default),
the driver reads the value from register `0xF3` at startup. Set this
only to override a wrong factory-stored calibration.

*va*='number';;
Override the apparent-power (VA) rating of the unit. The model id byte
reported by the firmware is shared between some product lines (for
example a 3200 VA "GT" unit reports the same id as the Easy 2200 TI),
so the driver cannot always tell them apart and may pick the wrong VA
rating from its model table. Setting *va* to the nameplate rating
corrects `ups.power.nominal`, `ups.realpower.nominal` (VA times the
0.7 power factor) and the computed `ups.load`.

*allow_shutdown*;;
Enable the `shutdown.return`, `shutdown.stayoff`, `shutdown.stop` and
`test.battery.start.deep` instant commands. Disabled by default for
safety: the Easy 2000 TI firmware does **not** auto-restart after a
coordinated shutdown, so an `upsmon`-driven shutdown on low battery
will leave the UPS (and everything plugged into it) powered off until
someone presses the physical power button. Only set this flag if you
have an out-of-band way to power the UPS back up, or if you are
deliberately running a UPS that should stay off after a critical-
battery event. With this flag unset, `upsdrv_shutdown` logs the
refusal and exits with failure instead of cutting the output.


FAMILY 14 (EASY WAY)
--------------------

The Easy Way units transmit a 32-byte frame about every 1.3 seconds on
their own, at 2560 baud 8N1, without being asked. The driver only
reads: it never writes anything to a family 14 unit, it registers no
instant commands, and `upsdrv_shutdown` fails (so the `FSD` handling of
`upsmon` cannot power such a UPS off through this driver). If
*allow_shutdown* is set it is ignored with a warning. No write command
is known for this family: the OEM device table lists no actions for it
and none was seen in captures of the OEM software.

Unlike family 10, these units do use the line speed, so the port must be
at 2560 baud (not the usual 2400: that is the first speed listed for this
family in the OEM device table, and the OEM software uses it); the driver
sets that itself. Read at 2400 the stream is corrupted in a systematic
way: bit 7 of the bytes arrives set and bit 6 is unreliable, so most
frames fail the checksum, and a few corrupted ones still pass it. A
speed like 2560 has no standard constant, so the driver asks the system
for it directly (the `termios2` interface on Linux, the numeric speed on
BSD and macOS). If that fails, for instance on a platform without such
support, the driver logs a warning ("could not set 2560 baud; falling
back to 2400, expect corrupted frames") and uses 2400; the checks below
then drop most frames and the data will often be marked stale.

The 8-bit sum of the frame is a weak check (two bytes that both gain bit
7 add up to zero), so a frame is only accepted if it also passes these:

* Registers 0x00 to 0x09 (version, model and calibration constants) are
fixed in the unit. They must equal a reference, which is taken from two
consecutive checksum-valid frames having identical values there; nothing
is published before that, so the start-up takes a few seconds longer. If
frames keep being dropped for this reason for more than 30 seconds and
two consecutive ones agree on other values, those become the new
reference.
* The tap index is at most 3, the load at most 150 %, the temperature at
most 100 degrees C and the battery voltage between 6 and 18 V.
* `ups.alarm` entries, `OVER` and `LB` appear, and disappear, only after
two consecutive accepted frames agree. `OL`, `OB` and `CHRG` follow
each accepted frame, so a mains cut is reported without that delay.

Published data: `ups.mfr`, `ups.model`, `ups.firmware`,
`ups.power.nominal`, `ups.temperature`, `ups.load`, `ups.status`,
`ups.alarm`, `input.voltage`, `input.voltage.nominal`,
`output.voltage`, `output.voltage.nominal`, `output.frequency`,
`output.frequency.nominal`, `battery.voltage`, `battery.voltage.nominal`
and `battery.charge`. There is no output current. `ups.load` is the
load ratio reported by the firmware. `ups.power.nominal` is the number
in the model name, with the same convention as for family 10;
`ups.realpower.nominal` is not published because the OEM table does not
say whether that number is VA or watts. `battery.charge` is an estimate
computed from the battery voltage, as in the OEM software, but that
voltage wobbles from frame to frame, and the NUT core reads every change
of `battery.charge` below 100 as charging or discharging. So the driver
publishes 100 flat while on mains with the battery-full flag set, and
otherwise a short exponential average of the estimate (about 5 s) that
never falls while `CHRG` is shown and never rises while on battery.
`battery.voltage` is the instant value. On battery the driver also sets
`DISCHRG`.

What was observed on hardware (mains cut and restored on one TI unit):
`OL` and `OB` follow the firmware's on-battery flag, and the voltages,
frequency, load, battery voltage and temperature match the values shown
by the OEM software. What is inferred from bit names in the OEM table
and was *not* observed: `CHRG` (shown while on mains and the
battery-full flag is clear), `LB`, `OVER`, and every `ups.alarm` entry.
`BOOST`, `TRIM` and the beeper are not reported. The M1 and M2
variants follow the OEM table, but the output voltage formula of the M2
(220 V) models in that table is the 115 V one with different tap factors,
which looks doubtful, so treat `output.voltage` on those with suspicion
until someone confirms it.

If no accepted frame arrives for more than five seconds the data is marked
stale.


CAVEATS
-------

The serial control lines DTR and RTS are forced low by the driver
immediately after opening the port. Non-zero levels on either line
are interpreted by the UPS as a remote shutdown signal -- never run
this driver alongside other software that toggles those lines on the
same device node.

On family 10, replies are framed by a 0xAA start byte and have no
checksum; the driver re-synchronizes by scanning for the start byte
after any short read. On family 14 the frames start with `55 55 AE` and
end with an 8-bit sum; the driver checks every frame whose sum is right
against the constants and ranges described above, and keeps the newest
one that passes.
